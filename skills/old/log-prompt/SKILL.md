# log-prompt

จงอ่านค่าตัวแปร `PROMPT_LOG_FILE_PATH` จากไฟล์ `.env` ในโปรเจกต์นี้ เพื่อระบุ Path ของไฟล์ Log (ถ้าไม่มีให้ใช้ค่าเริ่มต้นเป็น `prompt-experiments.md`) และสร้างหรือปรับปรุงไฟล์ดังกล่าว โดยใช้โครงสร้างตาราง Markdown ใหม่ดังต่อไปนี้:

| วันที่เวลา | AI Model | Session ID | สรุป Session | ไฟล์ที่เกี่ยวข้อง | การแก้ไขโดย AI | การแก้ไขโดย Developer | การวิเคราะห์ (เหตุผลที่ Developer ต้องแก้เอง) | สถานะ | Remark |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

## คำอธิบายแต่ละคอลัมน์ (Schema)

1. **วันที่เวลา** — เวลาปัจจุบันที่บันทึก (รูปแบบ `YYYY-MM-DD HH:mm`)
2. **AI Model** — ชื่อโมเดลที่ใช้ในการสนทนา Session นี้
3. **Session ID** — รหัสอ้างอิงของ Session (ถ้าไม่มี ให้สร้างจาก timestamp เช่น `S-YYYYMMDD-HHmm`)
4. **สรุป Session** — สรุปเป้าหมาย/โจทย์ของการคุยทั้ง Session แบบกระชับ (1–3 บรรทัด) ใช้ `<br>` คั่นบรรทัดได้
5. **ไฟล์ที่เกี่ยวข้อง** — รายการไฟล์ทั้งหมดที่ถูกแตะใน Session นี้ (คั่นด้วย `<br>`)
6. **การแก้ไขโดย AI** — สรุปสิ่งที่ AI แก้จริง โดย **ต้องตรวจสอบจากสถานะโค้ดจริง** ไม่ใช่จากที่ AI อ้างในแชท (ดู Workflow ข้อ 2)
7. **การแก้ไขโดย Developer** — สรุปสิ่งที่ Developer แก้เองในโค้ด (ส่วนต่างระหว่างสถานะปัจจุบัน กับสิ่งที่ AI แก้ไว้)
8. **การวิเคราะห์** — เหตุผลว่าทำไม Developer ต้องลงมือแก้เอง เช่น AI พลาดอะไร, เข้าใจผิดอะไร, ตก requirement ข้อไหน, หรือเป็นเรื่อง style/convention ที่ AI ไม่รู้
9. **สถานะ** — `✅ AI ทำสำเร็จ` / `⚠️ ต้องแก้บางส่วน` / `❌ Developer ต้องแก้เอง` / `🔄 ยังไม่เสร็จ`
10. **Remark** — หมายเหตุเพิ่มเติม (เช่น lesson learned, prompt ที่ควรใช้ครั้งหน้า)

## Workflow เมื่อ User พิมพ์ `/log`

1. **สรุปทั้ง Session** — สแกนประวัติการสนทนา **ทั้งหมดใน Session นี้** (ตั้งแต่ข้อความแรกจนถึงข้อความล่าสุดก่อน `/log`) เพื่อเข้าใจเป้าหมายและขอบเขตงาน
2. **ตรวจสอบโค้ดจริง (สำคัญที่สุด)** — ห้ามเชื่อแค่ที่ AI เคยพูดในแชท ต้องตรวจสอบสถานะจริงด้วยเครื่องมือ:
   - ใช้ `launch-process` รัน `git status` และ `git diff` (รวมถึง `git diff --staged`) เพื่อดูการเปลี่ยนแปลงทั้งหมดในโค้ด
   - ใช้ `git log --since="<เวลาเริ่ม session>" --name-status` หากมี commit ระหว่าง Session
   - ใช้ `view` อ่านไฟล์ที่ถูกแก้ เพื่อยืนยันเนื้อหาปัจจุบัน
3. **แยกแยะการแก้ไข** — เปรียบเทียบ 2 แหล่ง:
   - **สิ่งที่ AI เคยทำ**: ดูจาก tool calls ของ AI ใน Session (`str-replace-editor`, `save-file`, `remove-files` ฯลฯ)
   - **สิ่งที่อยู่ในโค้ดจริง ณ ตอนนี้**: ดูจาก `git diff` และไฟล์ปัจจุบัน
   - **ส่วนต่าง** = การแก้ไขโดย Developer (เช่น แก้ด้วยมือใน editor, revert บางส่วน, แก้ format)
4. **วิเคราะห์เหตุผล** — สำหรับทุกการแก้ไขโดย Developer ให้วิเคราะห์ว่าเพราะอะไร เช่น:
   - AI ใช้ API/ไลบรารีผิดเวอร์ชัน
   - AI ไม่ตาม coding convention ของโปรเจกต์
   - AI ตกเงื่อนไข edge case
   - AI เข้าใจ requirement ผิด
   - เป็นเรื่อง style/preference ส่วนตัว
5. **เขียนต่อท้ายไฟล์ Log** — Append แถวที่สรุปได้ลงไฟล์ที่ระบุใน `PROMPT_LOG_FILE_PATH` ทันที (ถ้าไฟล์ยังไม่มี header ให้สร้าง header ตามตารางด้านบนก่อน)
6. **ตอบกลับสั้นๆ** — หลังจากบันทึกเสร็จ ให้พิมพ์ตอบกลับในแชท **เฉพาะแถวตาราง Markdown ที่เพิ่งบันทึกไปเท่านั้น** ห้ามทักทาย ห้ามอธิบาย ห้ามใส่ข้อความอื่นใดเพิ่มเติม เพื่อประหยัด Context

## ข้อกำหนดเพิ่มเติม

- ถ้าใน Session ไม่มีการแก้โค้ดจริง (เป็นการคุย/ถามตอบเฉยๆ) ให้ใส่ `-` ในคอลัมน์ที่เกี่ยวกับโค้ด และระบุใน Remark ว่า "Discussion only"
- ในช่องที่มีหลายรายการ ให้ใช้ `<br>` คั่นบรรทัด และใช้ `` ` `` (backtick) ครอบชื่อไฟล์/ฟังก์ชัน
- ห้ามใช้อักขระ `|` ในเนื้อหาของเซลล์ (ใช้ `\|` หรือเลี่ยงคำอื่นแทน) เพื่อไม่ให้ตาราง Markdown เพี้ยน
- หากเคยบันทึก Session ID เดียวกันไปแล้ว ให้เพิ่มเป็นแถวใหม่ต่อท้าย (ไม่แก้ไขแถวเดิม) เพื่อรักษา audit trail

หากเข้าใจโครงสร้างและเงื่อนไขใหม่นี้แล้ว ให้จัดการไฟล์ Log ทันที และตอบกลับสั้นๆ ว่า "System Ready"
