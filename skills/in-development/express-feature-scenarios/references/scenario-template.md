# Scenario output contract

ใช้โครงสร้างนี้เป็น contract ไม่ใช่แบบฟอร์มตายตัว จำนวน Scenario และ Case เปลี่ยนตาม
Feature และหลักฐาน

```markdown
# <ชื่อ Feature>

เมนู: **<ตำแหน่งเมนู Express>**

<Feature ใช้ทำอะไร ใครเป็นผู้ใช้ ประโยชน์ และไม่ใช้ทำอะไร>

## Scenario 1: <เป้าหมายของผู้ใช้>

### ใช้เมื่อ

<สถานการณ์ที่ผู้ใช้ต้องการทำงานนี้>

### ข้อมูลที่ต้องกรอกหรือเลือก

| ช่อง | วิธีกรอก |
| --- | --- |
| <ชื่อช่องบนหน้าจอ> | <กรอกหรือเลือกอะไรและเมื่อใด> |

### วิธีใช้

1. <ขั้นตอนจากหน้าจอจริง>
2. <ขั้นตอนถัดไป>

### Case ที่เกิดขึ้นได้

#### Case 1.1: <รูปแบบการใช้งาน>

<สิ่งที่ผู้ใช้ทำและผลที่ได้รับ>

## Scenario 2: <เป้าหมายถัดไป>

<ทำซ้ำตามโครงสร้างที่จำเป็น>

## หลักฐานที่ใช้

- คู่มือ Express หัวข้อ `<ชื่อหัวข้อ>`
- ภาพหน้าจอ Express `<ชื่อไฟล์>`
- ผลเปรียบเทียบก่อน–หลัง `<ชื่อไฟล์>`
```

## Coverage pass

ก่อนส่ง draft ให้ Developer ตรวจ ให้ตรวจด้วยตนเองทีละข้อจากหลักฐาน ไม่ถามผู้ใช้:

- Feature มีวิธีสร้าง เปิดดู ค้นหา แก้ไข เรียกใช้ ยกเลิก หรือลบแบบใดบ้าง
- field ใดกรอกเสมอ กรอกตามเงื่อนไข เว้นว่างได้ หรือระบบเติมให้
- ค่าหรือทางเลือกใดทำให้ workflow ต่างกัน เช่น คงที่/ผันแปร มี/ไม่มีแผนก
- รองรับหลายบรรทัด รายการรวม Note shortcut หรือการเรียกจาก Feature อื่นหรือไม่
- มีผลต่อสิ่งที่ผู้ใช้เห็นหลังบันทึกอย่างไร
- มีคำสั่งใกล้เคียงที่ต้องแยกให้ชัดว่าไม่ใช่ Feature นี้หรือไม่

ใส่เฉพาะ branch ที่หลักฐานตอบผลลัพธ์ได้ ครอบคลุมทุก branch ที่พบ และไม่สร้าง
validation/error message ที่ Express ไม่ได้แสดง หากหลักฐานบังคับขาดให้กลับไปใช้
Evidence gate และหยุด

## Quality bar

- คนที่ใช้ Express อ่านแล้วทำตามได้โดยไม่รู้โครงสร้างระบบ
- AI อ่านแล้วรู้ทุก user-visible behavior ที่ต้องสร้างและทดสอบ
- ทุก Scenario ระบุ field, ขั้นตอน และผลลัพธ์
- ไม่มี Artemis link, Data Mapping, technical schema, `รอยืนยัน`, TODO หรือคำถามค้าง
- ชื่อเมนู field button shortcut และข้อความตรงกับหลักฐาน
